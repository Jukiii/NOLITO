# 0009 Phase 7 プロダクトの詳細ページ・サポート・配布(GitHub Releases)・外部販売の決定事項

日付: 2026-09-20 / 対象Phase: 7

## 仕様

`docs/01_phases/phase-07.md`: ソフト詳細は説明・画像・動作環境・FAQ・サポート。GitHub Releasesを初期利用し将来自動更新。販売は外部サービスから開始。

## スコープ

含めるもの: 詳細ページ(静的生成)、データ構造の拡張(`products.json` version 3)、`/software/`(一覧)、`/support/`(最小限)、カードの「詳細」ボタン、配布(GitHub Releases など、外部URLへのリンク)と外部販売のリンクの仕組み、「上司から逃げろ」の詳細ページ。

含めないもの(該当Phase・別途): 実際の有料ソフトの公開・販売サービスの選定・特定商取引法の表記・利用規約(Issue #12、P29・30)、お問い合わせ先の決定(Issue #13、P10)、GitHub Releases からの自動更新(P26)、`/downloads/` と `/tools/`(P8)、ナビ「ソフト」の有効化(最初のソフトを公開するとき)、共通詳細・カテゴリ絞り込み・検索(P20)、購入履歴・ライセンス(P9)。

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 詳細ページの作り方 | `products.json` の `detail_path` があるものを、`scripts/build-products.mjs`(`npm run build:products`)が**静的なHTML**として生成する。**生成物はコミットする**。`npm run check` の単体テストが、最新かを検査する。ページ先頭に生成の印を入れ、手書きのページを上書きしない・古い生成物を見つけて消す | 検索・SNS共有・広告審査(P29)に有利。JavaScriptなしでも読める。記事(P5)と同じ方式 |
| 2 | 生成物の整形 | 生成したHTMLを、ビルドの中で Prettier(プロジェクトの設定)で整形する | 生成物のためだけに `.prettierignore` を増やさず、`npm run format:check` を通す。整形は何度かけても同じ結果(テストで確認) |
| 3 | データ(version 3) | `detail_path`・`screenshots`(alt と width・height が必須。最大6枚)・`requirements`(項目名と値。最大20)・`faq`(質問と答え。最大20)・`purchase`(外部の販売サービス)を追加。すべて必須で、空・null にできる | 「動作環境」「FAQ」の形式は仕様に書かれていないため、管理画面(P26)から入力しやすい単純な形にした |
| 4 | 詳細ページの場所 | `detail_path` は、カテゴリの一覧ページの下の、小文字・数字・ハイフンの `/` 終わりのパス。他のプロダクトの `detail_path`・`url`、カテゴリの一覧ページと重複できない。手書きのページがある場所には、生成せずに失敗する | 取り違え・上書きを、保存前に止める |
| 5 | ソフトとゲームの違い | ソフトは、`url` = 詳細ページ(ボタンは、ダウンロードと購入)。ゲームは、遊ぶ先(`url`)と詳細ページ(`detail_path`)が別で、カードに「遊ぶ」と「詳細」が並ぶ | 詳細ページ自身へのリンクを出さないため |
| 6 | 配布(GitHub Releases) | `download.url` に、GitHub Releases のページなどの https の URL を書く。**リンクだけ**で、ページの表示時に GitHub などへ通信しない。ボタンの下に、移動先の注意書きを出す(GitHub Releases は、その旨を明示) | 外部通信を増やさない(プライバシーポリシーの版を上げずに済む)。API のレート制限も避ける。「将来自動更新」は、管理画面(P26)で、Releases から PR を作る形を検討する |
| 7 | 外部販売 | `purchase: { label, url }`(https の外部サービスだけ)。有料(paid)で、準備中でないものだけに付けられる。詳細ページに、購入ボタンと「購入の手続きは、外部の販売サービス(ホスト名)のページで行います」を出す。カードには出さない | 仕様「販売は外部サービスから開始」。有料のソフトを出す前に、サービスの選定・特定商取引法の表記・利用規約が要る(Issue #12) |
| 8 | サポート | `/support/` を最小限で追加(よくある質問へのリンク・お問い合わせ先は「準備中」・対応の方針)。フッターに「サポート」。詳細ページの「サポート」の節から `/support/` へ。文面は**下書き**で、運営者の確認が必要 | 詳細ページの「サポート」の行き先が必要。お問い合わせ先は Issue #13 |
| 9 | 「上司から逃げろ」の詳細ページ | `/games/escape-boss/about/` を作る。説明・画面3枚・動作環境・FAQ5件・更新履歴。内容は実装から起こした事実だけ(記録はブラウザにだけ保存、IME、複数のローマ字の書き方、会長の解放条件、ランキングは端末内) | 実データで、更新履歴・FAQ・動作環境がこのPhaseで初めて画面に出る。生成の仕組みを、実際のページで確認できる |
| 10 | 動作確認の記載 | 動作環境に「Microsoft Edge(Windows)で確認しています。ほかのブラウザやスマートフォンでの確認は、まだ十分ではありません」と書いた | 確認していないブラウザ・端末を、動くと書かない。**運営者が確認した範囲を、あとで書き換える** |
| 11 | 画面の画像 | ゲームのスタート・プレイ中・結果の画面を、headless Edge で 1000x700 の WebP に撮って `public/assets/img/products/escape-boss/` に置いた(約 90KB 合計)。ゲームの画面を変えたら撮り直す | 詳細ページの「画像」。alt と width・height つき |
| 12 | `/software/` とナビ | 一覧ページは作る(いまは0件で「まだ公開しているものがありません」)。ナビの「ソフト」は、最初のソフトを公開するまで「準備中」のまま | 空のページへ誘導しない。切り替えは `nav.js` の1行 |
| 13 | ページの題名 | 詳細ページの `<title>` は「○○の詳細 \| NOLITO」。ゲーム本体のページの題名(○○ \| NOLITO)と区別する | 検索結果・タブで、同じ題名が2つ並ばないように |
| 14 | プライバシーポリシー | 変更しない(版も上げない) | 実行時の外部通信・保存する情報が増えていない。外部リンクは、移動先のサービスの規約による(購入リンクを使う商品を出すときに、Issue #12 で再検討) |
