# 0014 Phase 9 PR 2: ライセンスキーの決定事項

日付: 2026-09-20 / 対象: Phase 9「プロフィール・成績・購入履歴・ライセンスを管理。ライセンスキー＋アカウント認証」の後半(前半は 0013)。

## 背景と方針

- 仕様は1行で、細部がない。**有料のソフトも、販売サービスもまだない**(Issue #12 は未決)。購入履歴に載せるデータの出どころが、いまはない。有料機能を使えるかどうかの制御は、仕様では Phase 29 以降。
- そこで、**最小の形**にする: ライセンスキーの登録・一覧・運営者による発行だけ。購入履歴は、作らない(「入手履歴」=登録したライセンスの記録に置き換える)。

## スコープ

- **含める**: キーの登録、自分のライセンスの一覧、発行スクリプト(運営者用)、無効化の手順(SQL)、アカウント削除との関係、`licenses` テーブル
- **含めない**: 購入データの取り込み・購入履歴・決済(Issue #12 と、販売サービスの選定の後)、有料機能の実際の制御(Phase 29 以降)、発行・無効化の管理画面(Phase 26 以降)、キーの他アカウントへの移行、端末数の制限、有効期限、複数のキーの1回での登録

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 範囲 | 登録・一覧・発行(運営者)。購入履歴は作らず、「入手履歴」(登録したライセンスの記録。一覧の「登録日」)で代える。一覧の近くに「有料の配布は、まだ始まっていません」と書く | データがない機能を、作らない。販売サービスが決まってから、購入データのつなぎ方を決める |
| 2 | キー | `NLTO-XXXXX-XXXXX-XXXXX-XXXXX`。20 文字 × 5 ビット = **100 ビット**の乱数(`crypto.getRandomValues`)。Crockford の Base32(I・L・O・U を使わない)。偏りが出ない(256 が 32 で割り切れる) | 推測できない。読み間違えにくい |
| 3 | 入力の許容 | 大文字・小文字、空白、ハイフンの有無、読み間違えやすい文字(O→0、I・L→1)を、直して受ける。形が違えば `400 license-format` | 手で写すときの失敗を減らす |
| 4 | 保存 | **SHA-256 のハッシュ(`license:` + 正規のキー)と、末尾 4 文字(ヒント)だけ**。キーそのものは、DB にも、監査ログにも、スクリプトの出力の SQL にも入れない。画面には、ヒントだけを出す | DB が漏れても、キーは分からない。100 ビットなので、ソルト・ペッパーなしで足りる |
| 5 | 発行 | `node scripts/issue-license.mjs <商品ID> [--count 1〜50] [--note メモ]`。キーと、D1 の Console に貼る `INSERT`(1 行に 1 文・**コメントなし**)を、画面に出す。**キーは、この画面にしか出ない**(ファイルに書かない・外へ送らない)。商品 ID は `products.json` にあるものだけ。メモは 100 文字まで・制御文字不可・単一引用符は打ち消す | 管理画面・発行の API を作らない(攻撃面を増やさない)。新しい秘密の値も要らない |
| 6 | 登録 | `POST /api/licenses/redeem`(`{ "key": "..." }`)。PR 1 と同じ CSRF 対策・招待制の確認を通す。**1 つの条件つき `UPDATE`**(未登録・無効でない)で行うので、同時に 2 人が登録しても、成功するのは 1 人 | 二重に使われない |
| 7 | 失敗の応答 | 存在しない・**他の人が使用済み**・無効は、**同じ応答**(`400 license-invalid`)。自分がすでに登録したキーは、何度でも成功(`already: true`。監査ログは増やさない) | キーの存在・使用状況を、探れないようにする |
| 8 | 回数の制限 | 1 人あたり **5 回 / 10 分**、送信元(IP の HMAC)ごとに **20 回 / 10 分**。制限中は、正しいキーでも通らない(429) | 総当たりを防ぐ。100 ビットなので、実際には当たらないが、入口で止める |
| 9 | 一覧 | `GET /api/licenses`。自分のものだけ・新しい登録順。返すのは `id`・`productId`・`hint`・`redeemedAt`・`status`(`active` / `revoked`)だけ(キーの全体・ハッシュ・メモ・`user_id` は返さない)。商品名は、画面が、公開の `products.json` から引く | 内部の情報を出さない |
| 10 | 無効化 | 運営者が、D1 の Console で `revoked_at` を入れる(手順書)。無効のものは、一覧に「無効」と残り(文字と破線の枠。色だけにしない)、登録できない | 返金・誤発行などに、管理画面なしで対応する |
| 11 | アカウントの削除 | **ライセンスの記録は残し、結びつき(`user_id`・`redeemed_at`)だけを外す**。同じキーを、また登録できる。削除した人を特定できる情報は、ライセンスに残らない。外部キーは `ON DELETE SET NULL`(運営者が SQL で直接消したときの保険) | 買った・受け取った権利が、アカウントの削除で消えない。個人情報は残さない |
| 12 | 監査ログ | 成功: `license-redeem`(`detail` は商品 ID)、失敗: `license-redeem-failed`。**キーは入れない** | 個人情報・秘密を入れない |
| 13 | プライバシー | ポリシーの版は**上げない**(v1 のまま)。限定公開の間は、`/account/` に「ライセンスは、アカウントに結びつけて保存する」「削除すると外れる」と書いた。ライセンスと利用者の結びつきは、個人に関わる情報なので、一般公開の前に、ポリシー v2 に書く(Issue #19) | 招待した少数の方への限定的な提供。0013 の方針と同じ |
| 14 | 手順書の SQL | D1 の Console は、貼った SQL の**改行を消して 1 行にすることがある**(実際に、PR 1 の SQL が、`--` のコメントで、全部コメントになり `Requests without any query are not supported` になった)。**手順書の SQL は、コメントを抜き**、`migrations/` のファイルと同じ内容であることを、テストで守る(`tests/migrations-doc.test.js`)。運営の操作の SQL も、コメントなし・1 回に 1 文 | 運営者が貼るものは、貼り方に強くする |
| 15 | 保存形式(D1) | `migrations/0002_licenses.sql`(`licenses`。時刻は UNIX 秒)。0001 は書き換えない | 本番の DB に、順番に適用する |

## 画面(`/account/`)

- 「ライセンス」の節: キーの入力(自動補完オフ・スペルチェックオフ・必須)、一覧(商品名・`キー: NLTO-…-XXXX`・登録日・状態)、空の案内。表示は、すべて `textContent`。
- 結果の知らせは、**一覧を更新してから**出す(「登録しました」と聞こえたのに、一覧にない、を作らない)。一覧の更新に失敗したときは、登録できたことと、失敗を、一緒に伝える。
- 失敗のメッセージ(`license-format`・`license-invalid`)は、`messages.js` に追加(既存のテストが、サーバーのエラーの種類と、文の対応を検査する)。

## テスト方法

- 単体・結合(`node --test`): キーの生成(形・重複・偏り)・正規化・ハッシュ(10)、API(22: 登録・重複・他人の使用済みが未登録と同じ応答・無効・同時登録・ハッシュだけの保存・監査ログ・401・403・CSRF・回数制限(1 人・IP)・一覧・削除との関係)、発行スクリプト(12: 出力の SQL を DB に流して、キーがそのまま登録できること・SQL インジェクションしないこと・入力の検査・コマンドの終了コード・キーを保存しないこと)、手順書と `migrations/` の一致(5)、ページ・クライアント(7 追加)
- ブラウザ(headless Edge)+ **`wrangler pages dev`(本物の workerd・D1)** + 偽の Google: **発行スクリプトを実際に実行**して、出力の SQL をそのまま D1 に流し、画面で登録 → 一覧 → 重複 → 形の違い → 存在しない → 回数制限 → 別の人 → 無効 → 削除 → 再登録 → 別オリジンからの登録 → 375px までを通した

## 見つけて直した不具合

- 「登録しました」の知らせが、一覧の更新より先に出ていた(一覧を更新してから、知らせるように)
- テストの誤り(実装の不具合ではない): 回数の制限(5 回)を超える回数で、形の違うキーを試していた

## 未確認・既知事項

- **マージの前に、本番の D1 に `0002_licenses.sql` を実行する必要がある**(手順書の「0002」を、Console に貼る)。実行前にマージすると、`/api/licenses` が 500 になり、アカウントページのライセンスの節に、エラーが出る(ログイン・ニックネームなど、ほかの機能は、動く)
- **有料機能を使えるかどうかの制御は、ない**。ライセンスの登録・一覧だけ。これを使って、機能を出し分けるのは、有料の商品と販売サービスが決まってから
- 購入履歴は、作っていない(販売サービスが決まってから)
- キーは、手渡し(運営者が、控えて、渡す)。発行・無効化の管理画面はない(Phase 26 以降)
- 運営者が、D1 の Console で `DELETE FROM users` だけを実行すると、ライセンスの `redeemed_at` が残る(`user_id` は NULL になる)。登録には影響しない(`user_id IS NULL` で判定)が、手順書の 2 文(先に `UPDATE licenses ...`)を使う
- ライセンスと利用者の結びつきは、個人に関わる情報。一般公開の前に、ポリシー v2 に書く(Issue #19)
- ブラウザは、Microsoft Edge(Windows・headless)だけで確認。実機・スクリーンリーダーは未確認
