# 0022 Phase 12 PR 3: 距離の計算(難易度・速さ)とバランスの再調整

日付: 2026-09-21 / 対象: Phase 12「文字数・難易度・速度で正解時距離増加、ミス・長さで減少」。PR 1(0019)・PR 2(0020)の続きで、Phase 12 の最後の PR。

## 運営者が決めたこと(計画への「推奨案で」)

1. **速さの測り方**: 語ごとの打鍵/秒で、**加算だけ**(コンボなどのルールは足さない)
2. **バランスの目標**: **0006 の表に戻す**(役職ごとの難しさの階段を保つ)
3. **距離が増えた量の表示**: **出さない**(仕様にない)。FAQ と説明で伝える
4. 「長さで減少」は、0019 の決定 8 のまま(新しいルールは、作らない)

## 仕様と、現状の突き合わせ

| 仕様 | 状態 |
| ---- | ---- |
| 文字数で距離が増加 | 済み(`gain_per_char × 文字数`) |
| **難易度で距離が増加** | **この PR**。語録の `difficulty`(Phase 11 で、読みの長さの決めにそろえた)を使う |
| **速度で距離が増加** | **この PR**。語ごとの打鍵/秒 |
| ミス・長さで減少 | 済み(ミスは `miss_penalty`。長い語ほど、打つ間に時間で縮まる) |

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 式 | 1 語の正解で増える距離 = **基本(`base_gain`)+ 文字数の分(`gain_per_char × 標準の表記の長さ`)+ 難易度の分 + 速さの分**。合計は、`max_distance` で頭打ち | 仕様の 3 つ(文字数・難易度・速度)を、足し算で |
| 2 | 難易度の分 | `difficulty_gain × (難易度 − 1)`。難易度 1 は 0、2 は +1、3 は +2(`difficulty_gain` = 1)。語録の範囲(1〜5)の外は範囲に収め、数でない値・項目がない stage は 0 | 難易度は読みの長さの決め(0006)なので、文字数の分と重なる。段差の上乗せで、人が難易度を付け直す(将来)ときの調整のつまみにもなる |
| 3 | 速さの分 | `speed_gain × clamp((打鍵/秒 − speed_min_cps) ÷ (speed_max_cps − speed_min_cps), 0, 1)`。**`speed_gain` = 3、min = 2、max = 6 打鍵/秒**。min 以下は 0、max 以上は 3(頭打ち)。**加算だけ**(遅くても、減らない) | 遅い人が、いまより不利にならない |
| 4 | 速さの測り方 | 語の**最初の正しい打鍵から、最後の打鍵まで**の間隔(打鍵数 − 1)÷ かかった秒数。語と語のあいだの反応の時間は入らない。打鍵数は、**実際に打った数**(`matcher.typed`。si と shi など、書き方の違いに左右されない)。秒は、**ゲーム内の経過秒**(`state.elapsed`。タブが見えない間は進まない)。語ごとに測り直す | 打つ速さだけを測る。時計を、ゲームの中に一本化 |
| 5 | 不正な値 | 秒数が 0 以下・数でない・無限、打鍵数が 2 未満は、速さの分 0(NaN にならない。連打・自動入力でも、極端な加点が出ない) | 落ちない・悪用しにくい |
| 6 | エンジン | `engine.js` に `typingSpeed`・`difficultyGain`・`speedGain` を足し、`wordGain(stage, 文字数, { difficulty, seconds, keystrokes })`・`applyCorrect(…, options)`。**options がなければ、従来どおり(文字数の分まで)**。DOM・時計・乱数に触れない | 純粋なロジックのまま。テストしやすい |
| 7 | データ | `roles.json` の各 `stage` に `difficulty_gain`・`speed_gain`・`speed_min_cps`・`speed_max_cps` を足す(全役職で同じ値。役職ごとに変えることも、できる)。**`base_gain` を再調整**(下記)。`tests/data.test.js` が、項目の存在・正の数・`min < max` を検査 | データで調整できる |
| 8 | 用語確認 | 影響なし(追いかけも距離もない) | 0019 |
| 9 | 表示 | 増えた距離の量は、**出さない**。ゲームのページの遊び方・詳細ページの説明・FAQ「正解したとき、距離はどれだけ広がりますか?」で伝える | 運営者が(a)を選んだ |
| 10 | 保存・スコア | **記録の形・版(`DATA_VERSION` 2)・スコアの式は、変えない**。ただし、スコアには「残り距離 × 5」が入っているため、速く打つと、残り距離が増え、**スコアが、以前より少し高くなる**(以前の記録とは、少し違う尺度になる。ランキングは、この端末の中だけ) | 仕様にないので、式は変えない。この影響は、記録しておく |
| 11 | 語録 | 変えない | 語録の版・確認シートは、そのまま |

## バランス

同じシミュレーション(実際の語録・エンジン・打鍵の 4 モデル・各 4000 回。ふつう = 2.5 打鍵/秒・ミス 8%、遅い = 1.2・8%、速い = 4・5%、達人 = 6・3%)。クリア率(%)。

| 役職 | 遅い | ふつう | 速い | 達人 |
| ---- | ---- | ---- | ---- | ---- |
| **0006 の表(目標)** | 先輩 87 | 係長 89 / 部長 67 / 社長 50 | 会長 75 | 100 |
| 現行(0021)・加点なし | 先輩 87 | 係長 88 / 部長 67 / 社長 53 | 会長 76 | 100 |
| 加点を足して、`base_gain` はそのまま | 先輩 98 | 係長 99 / 部長 92 / 社長 85 | 会長 99 | 100 |
| **加点を足して、`base_gain` を調整(採用)** | **先輩 86** | **係長 89 / 部長 67 / 社長 48** | **会長 76** | **100** |

- 加点だけを足すと、ふつうの人でも社長を 85% でクリアしてしまい、階段が崩れる。そこで、役職ごとの目標のクリア率(0006)に合わせて `base_gain` を探した(二分法): **先輩 5 → 3.9、係長 5 → 3.8、部長 5 → 3.7、社長 5 → 3.6、会長 4 → 1.7**。`drain_per_second`・初期距離・ミスの減り・目標語数は、変えない
- **会長の `base_gain` が大きく下がる**のは、会長の目標が「速い人」の 76% で、速さの加点(速い人は、1 語で平均 +1.5)が、いちばん効くため。速い人には、加点で、いまと同じように挑戦できる。ふつうの人は、0%(裏ボス)のまま
- 所要時間は、これまでと同じ(先輩・ふつう 約 65 秒、達人 約 29 秒。1 プレイ 1〜3 分)
- 残り距離(クリア時)は、速い人・達人で、増えた(たとえば、係長・速い 75 → 90)。速く打った分が、余裕(とスコア)になる
- **頑健さの確認**: 語ごとの打鍵速度に ±20% のばらつきを入れても、先輩 83・係長 87・部長 63・社長 46・会長 73(目標から 4 ポイント以内)
- **`tests/balance.test.js`** が、実際の語録・役職・エンジンで、決まった乱数の 1000 回のシミュレーションを行い、上の階段(先輩の遅い人 75〜95%、係長・部長・社長のふつうの人が 89 → 67 → 50 の近く、会長の速い人 62〜88%、達人はすべてクリア、速い人ほど下がらない、所要時間)から大きくずれたら、失敗する。**語録・`roles.json`・式を変えたら、このテストとシミュレーションで、見直す**(CLAUDE.md)
- これは、**モデルの打鍵での目安**で、実際の人間の手ごたえは、未確認(遊んで調整する)
