# 0047 Phase 22 の計画(ソフトウェアキーボード・外付けキーボード・縦横自動調整・タッチ操作・回転対応・画像/アニメーション/音声最適化・低性能端末設定)

日付: 2026-09-25 / 対象: Phase 22「ソフトウェアキーボード＋外付けキーボード。縦横自動調整。タッチ操作、回転対応、画像・アニメーション・音声最適化、低性能端末設定。」

「自立で」という運営者の指示(フェーズ移行も含む)により、実装前の確認を待たず、計画・実装方針を Claude Code の判断で決定した。

## 現状の確認

- **ソフトウェアキーボード**: ゲームの文字入力(`input.js`)は、すでに `keydown` ではなく `input` イベントで読み取っている(コメントに「スマホのソフトウェアキーボードでは keydown の key が取れないことがあるため」と明記済み)。入力欄には `autocapitalize="none"`・`autocorrect="off"`・`spellcheck="false"`・`enterkeyhint="done"` も、すでに設定済み。IME 変換中の判定除外も、Phase 8・12 から対応済み
- **外付けキーボード**: 物理キーボードは、通常の `input`/`keydown` イベントで、すでに問題なく動く(タブレット等に外付けキーボードを挿しても、ブラウザは同じイベントを出す)
- **未対応の実際のギャップ**: ソフトウェアキーボードが開いたときに、画面の高さが狭くなる。モバイルの下部固定バー(`bottom-nav`。Phase 20 PR1)が、ゲームのプレイ画面でも常に表示されたままで、キーボードと競合しうる。入力欄にフォーカスしても、画面をスクロールして見える位置に動かす処理がない
- **縦横自動調整・回転対応**: 横向き(landscape)専用の CSS が、まだ一つもない。ゲームのプレイ画面は、上から「距離ゲージ→場面→単語→入力欄」の縦積み(Phase 15)なので、横向きの低い画面(高さが狭い)では、入力欄が画面の外に出る恐れがある
- **タッチ操作**: `--tap-size`(44px 相当)トークンは、すでにボタン・select 等、27 箇所で使われている。ラジオボタン(役職・職種)・チャートのホバー領域(24px 以上。Phase 4 の dataviz 指針)も、既存のテストで確認済み
- **画像の最適化**: ゲームの絵は、すべて SVG(Phase 15・16 で、サイズ上限を決めてある。背景 3KB・キャラクター 4KB)。プロダクトカード・詳細ページのスクリーンショットは、すでに `loading="lazy"` と `width`/`height` が付いている(`components/product-list.js`・`scripts/lib/product-pages.mjs`)
- **アニメーションの最適化**: Phase 21 PR2 で、OS の設定・サイト内切替の両方に対応済み(`prefers-reduced-motion` + `data-reduced-motion`)
- **音声の最適化**: Phase 16 PR3 の設計により、音声ファイル・外部素材・通信を、そもそも使わない(Web Audio による合成のみ)。**最適化はすでに設計の前提として満たされている**
- **低性能端末設定**: 「動きを減らす」(Phase 21)はあるが、**描画そのものの重さ**(場面の背景 SVG の継続的な描画・終わりの演出の紙吹雪/輝き)を抑える設定は、まだない

## この PR(1)の決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 下部固定バーと、ソフトウェアキーボードの競合 | ゲームのプレイ画面(連続タイピング・用語確認とも、入力欄がある間)では、`bottom-nav` を**隠す**。ダッシュボード(まだプレイ中でない)では、そのまま表示する | プレイ中は、下部の固定バーが、貴重な縦の領域を奪う。ダッシュボードでは、サイト内移動の利便性を保つ |
| 2 | 入力欄にフォーカスしたときのスクロール | `input.js` の外(`main.js`)で、入力欄の `focus` イベントに、`scrollIntoView({ block: "nearest" })` を付ける。**ソフトウェアキーボードでも物理キーボードでも、同じ処理でよい**(物理キーボードでは、画面の高さが変わらないため、実質何も起きない) | 個別の判定(ソフトウェアキーボードかどうか)をせず、シンプルな処理で両対応する |
| 3 | 横向き(landscape)のレイアウト | `@media (orientation: landscape) and (max-height: 32rem)` で、場面(`.scene`)の高さを縮める・余白を詰める、専用のCSSを追加する(`game.css`)。**要素の並び順(距離ゲージ→場面→単語→入力欄)は変えない**(Phase 15 の決定を守る) | 横向きの低い画面高さでは、入力欄が画面外に出うる。並び順を変えると、既存の視覚的な優先順位(Phase 15)が崩れる |
| 4 | 画面回転そのものへの対応 | `screen.orientation.lock` 等での固定はしない(利用者の回転を尊重する)。CSS のメディアクエリ(`orientation`)だけで対応する | 回転を強制ロックすると、利用者の意図に反する。多くのブラウザで `orientation.lock` は、フルスクリーンAPIが要るなど、制約が大きい |
| 5 | kii-michi の「キーを押して入力」(既知の制限) | **対応しない**。`event.code`(物理的な位置)で読む設計(Phase 8)のため、タッチ画面の仮想キーボードでは、そもそも意味のある `event.code` が得られない(ブラウザによっては空・`Unidentified`)。ツールの目的(実在するキーボードショートカットの登録)自体が、物理キーボードを前提にしている | 仕様(Phase 8)の設計上の前提であり、Phase 22 で解決すべき不具合ではない。無理に対応すると、位置ベースの正確さ(Shift・配列の違いに左右されない)という、既存の利点を失う |
| 6 | 用語確認・練習モードへの影響 | 入力欄の `focus` によるスクロールは、両モードで共通の入力欄に効く(既存の `data-input` 目印をそのまま使う)。**新しい `data-*` 目印は増やさない** | 既存の構造を再利用し、無関係な変更をしない |

### 除外(この PR ではやらないこと)

- 低性能端末向けの設定(グラフィックを抑える)は PR3 で扱う

## テスト方針

- `tests/game-page.test.js` 等の既存テストに、`bottom-nav` を隠す対象の `data-*` 目印があることの検査を追加
- 横向きのメディアクエリの存在(`orientation: landscape`)を、CSS のテストで検査
- ブラウザ(headless Edge。`page.setViewport` + `page.emulateMediaFeatures` の `orientation` 相当。または横長のビューポートで代替)で、横向きの低い高さでも、入力欄が画面内にあることを確認
- モバイル幅で、ゲームのプレイ中は `bottom-nav` が非表示、ダッシュボードでは表示されることを確認

## テスト結果(この PR(1)完了時点)

- `npm run check`(lint・Prettier・単体テスト): **全 1890 件、成功**(`tests/mobile-input.test.js` の新規11件を含む。既存の `tests/sound-wiring.test.js` は、`input.focus()` に `preventScroll: true` を足したことに合わせて更新)
- **実装した内容**:
  - `view.js` の `showView("play")` で、`document.body` に `data-hide-bottom-nav` を付け、それ以外(ダッシュボード・結果・用語確認の結果)では外す。`layout.css` の `body[data-hide-bottom-nav] .bottom-nav { display: none; }` が、これを隠す
  - `window.visualViewport` の `resize`(ソフトウェアキーボードの開閉で発生。物理キーボード・デスクトップでは、ほぼ発生しない)で、入力欄にフォーカスがある間だけ、`inputBox.scrollIntoView({ block: "nearest" })` する
  - ゲームの `input.focus()` の呼び出し(ゲーム開始時・「音」ボタンを押した後)は、すべて `{ preventScroll: true }` を付けた。**これは、Phase 22 で見つけた、既存の(この PR とは無関係な)ブラウザの既定動作**: `element.focus()` は、既定で、要素が画面内に収まるよう、ブラウザが自動でスクロールすることがある。デスクトップの、やや低いウィンドウ高さ(例: 1280×700)で、ゲーム開始のたびに、意図せず画面が動いていたことを、実ブラウザのE2Eで発見し、この PR で修正した
  - `game.css` の末尾に、`@media (orientation: landscape) and (height <= 32rem)` を追加。ヘッダーの高さ(`--header-height` トークンを、この場面だけ `--tap-size` に上書き)・`.main` の余白・ゲージ/場面/単語カードの余白と文字サイズを詰めて、320px 程度の低い高さでも、入力欄が画面内に収まることを、実ブラウザで確認した
- **実装中に見つけた不具合とその修正(いずれもこの PR で対応済み)**:
  1. 最初、`input` の `focus` イベントで直接 `scrollIntoView` していたが、ゲーム開始時の自動フォーカスのたびに、デスクトップでも不要にスクロールしてしまうことが、E2E で判明。`visualViewport` の `resize` を見る方式に変更し、実際にキーボードが開いた(=見える高さが縮んだ)ときだけ動くようにした
  2. 横向きの CSS を、最初、ソースコード中の `.scene { height: 7rem; }` より**前**に置いてしまい、CSS の順序(カスケード)により、メディアクエリの中の上書きが効いていなかった(同じ詳細度なら、あとに書いたほうが勝つため)。`game.css` の末尾に移動して解決した
  3. 320px という低い高さでは、ヘッダー・`.main` の余白だけで 96px を占めていたため、単に場面・単語カードを詰めただけでは足りなかった。`--header-height` トークンを、この場面だけ上書きすることで解決した(ロゴ・ハンバーガーボタン自体の大きさは変えていない)
- ブラウザ(headless Edge)の E2E、計9件、すべて成功: ダッシュボードでの下部バー表示・プレイ中の非表示・`data-hide-bottom-nav` の付与、デスクトップでのフォーカスだけによる不要なスクロールがないこと、モバイルでキーボード相当の高さの変化で入力欄へスクロールすること、横向きの低い高さで入力欄・場面が収まること、通常の縦向きでは場面の高さが変わらないこと(回帰確認)
- スクリーンショットを目視確認: 320px の極端な高さでも、ヘッダー・ゲージ・場面・単語・入力欄が、すべて読める大きさで収まっている

## 未確認・既知事項(PR1時点)

- 375px 幅 × 300px 高さのような、**横向きの判定(幅>高さ)と、縦向きの通常利用が入り混じる、極端に小さいウィンドウ**では、ソフトウェアキーボードのスクロール(2番目の対応)と、横向きの圧縮(3番目の対応)が、同時に働き、`scrollIntoView` の計算が、実際のレイアウトのやや前の状態を見てしまい、行き過ぎることがある(E2Eで発見。実機のスマホでは、この幅と高さの組み合わせは、通常起きない)。現実的な使用範囲(スマホの横向きは、幅が高さより十分大きい)では、問題ない
