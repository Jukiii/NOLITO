# 0043 Phase 19 PR 2: ゲームの記録のアカウント移行(同期)

日付: 2026-09-24 / 対象: Phase 19 PR 2(0042 の計画のとおり)。「全部おすすめで決めて自立で進めて」という運営者の指示により、実装前の確認を待たず、以下を Claude Code の判断で決定した。

## 背景

0042 で、PR2(アカウント移行)・PR3(オンラインランキング)は、ゲームの記録を初めて運営者のサーバー(D1)に送る、privacy-sensitive な変更のため、着手前にプライバシーポリシーの改定内容を運営者に確認する、としていた。運営者から「全部おすすめで決めて自立で進めて」の指示があったため、この確認手順を、Claude Code 自身の判断(本 ADR での記録)に置き換えて、実装を進めた。

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 送る範囲(データ最小化) | **「要約」だけ**(ニックネーム・称号・経験値・職種ごとの合計・難易度ごとのクリア数・自己ベスト・実績の解放状況)を送る。**1プレイごとの詳細な記録(`results`。打鍵ごとの集計・打ち間違いの組・語ごとのミス数を含む)は、送らない**(端末にとどめる) | プライバシーへの影響を、必要最小限にする。詳細な履歴まで引き継ぎたい場合は、PR1 の JSON 書き出し・読み込み(端末間で直接移す。サーバーを経由しない)を使う、という役割分担にした |
| 2 | 送るタイミング | **利用者が、アカウントのページのボタンを押したときだけ**(「この端末の記録を、アカウントに保存する」)。ログインしただけでは送らない。自動同期はしない | 「任意(強制しない)」という 0042 の方針どおり。ゲームのプレイ中に、通信・保存の判断をさせない(プレイ画面はアカウント機能に触れない) |
| 3 | 検証のしくみ | サーバー側の新しい検証を書かず、**クライアント側の `normalizeData` を、そのまま使う**新しい関数 `normalizeSyncProgress`(`storage.js`)を作り、サーバー(`functions/_lib/game-sync.js`)も、同じ関数を import して使う | 検証・移行のしくみを重複させない(既存の方針と同じ)。不正な値は、項目ごとに既定値に整え、全体は断らない、という既存の安全側の挙動を、そのまま踏襲できる |
| 4 | 保存の形(D1) | 新しいテーブル `game_progress`(`user_id` 主キー。1 アカウントにつき 1 行、上書き)。`migrations/0004_game_sync.sql`。配列・オブジェクトの項目(`clears`・`jobs`・`difficultyClears`・`bests`・`achievements`)は、JSON の文字列として保存する | アカウントごとに、最新の要約だけを持てばよい(オンラインランキング用の別の構造は PR3 で検討) |
| 5 | 読み込みの動作 | 書き出し(PR1)と同じ、**置き換え**(アカウントの要約で、この端末のプロフィール・進行状況を、まるごと置き換える。マージしない)。結果の履歴・ランキングは、要約に含まれないので、そのまま残る | PR1 の JSON 読み込みと、同じ考え方に揃える |
| 6 | 画面の場所・確認 | アカウントのページ(`/account/`)に「ゲームの記録」の節を追加。**アップロード(端末→アカウント)は、即時実行**(自分のアカウントへの保存で、取り消せなくもない=もう一度送れば戻せる)。**ダウンロード(アカウント→端末)は、確認ダイアログ**(PR1 の取り込みダイアログと同じ部品 `modal.js`)を経由する(端末のデータを置き換える、取り消しにくい操作のため) | 操作の重さに応じて、確認の要否を変える(既存の削除ダイアログ・取り込みダイアログと同じ考え方) |
| 7 | アカウント削除時の扱い | `deleteUser` に `DELETE FROM game_progress WHERE user_id = ?` を追加(D1 は外部キーの `ON DELETE CASCADE` を自動で行わないため、明示的に消す)。この端末のブラウザの記録は、消えない | 既存の「アカウントを削除すると、アカウントに結びついた情報は消える」という設計(ライセンスは結びつきだけ外す/セッションは消す、と同じ並び)。アカウントに保存した要約は、アカウント固有の情報なので、削除する |
| 8 | レート制限・監査 | `hit()` で 30 回 / 10 分(他の書き込み API と同程度)。`audit.js` に `gameSyncSave` を追加(保存した事実だけを記録し、内容は記録しない) | 既存の他の API と同じ方針 |
| 9 | プライバシーポリシー | **版を 3 に上げる**(6-2-1 を新設し、取得する情報・取得する場合・利用目的・削除を明記)。`analyticsConfig.policyVersion` も 3 にし、既存の同意を無効にする(バナーを、もう一度出す) | ゲームの記録をサーバーに送るという、新しい種類の個人情報の取得(CLAUDE.md の「個人情報の取り扱いの変更…で上げる」に該当)。音の設定などの「端末内の保存」の追記とは異なり、社外(運営者のサーバー)への送信を新しく始めるため、版を上げる判断とした |
| 10 | 初回アクセス時の案内 | ダッシュボード(`/games/escape-boss/`)に、控えめな案内(バナー)を追加。**未ログイン・アカウント機能が使える環境でだけ**表示し、「閉じる」で以後表示しない(`nolito:escape-boss:account-banner-dismissed:v1`。記録の版付きデータとは別の、単純な印)。ログイン状態の確認は、アカウントの API クライアント(`fetchMe`)を再利用する | 「控えめなバナー」という 0042 の方針どおり。何度も出して邪魔をしない |

## 招待制のままでよいか

0042 の想定どおり、**招待制(Issue #19)のまま実装した**。アカウントを持つ人(=招待された人)だけが対象の機能で、一般公開の判断とは分けられるため。

## 未確認・既知事項

- 本番の D1 への `migrations/0004_game_sync.sql` の適用は、このブランチのマージ後に、運営者の認証情報を使って実施する(0003 と同じ手順)
- プロフィール(ニックネーム・称号)の同期は、アカウントのニックネーム(6-2)とは別の項目のまま(ゲーム内の表示専用)。将来、両者を統合するかは、未決定
- オンラインランキング(PR3)は、この PR の `game_progress` テーブル(1 アカウント 1 行の要約)だけでは、「上位 N 件」のようなランキング向けの問い合わせに向かない可能性がある。PR3 着手時に、別のテーブル・索引の要否を検討する
