# 0053: Phase 28 の計画・PR1(キャッシュ制御)

## 背景

Phase 27 は、RBAC・権限チェック・監査ログ(Phase 9・26)、再認証・依存の脆弱性チェック・依存の自動更新・復元テスト・監査ログのマスク・バックアップの世代管理(PR1〜6)まで完了した。残る「将来MFA」「暗号化」は、仕様が「将来」「抽象的」で、対象が具体化していない。運営者が 1 人の現状では優先度が低いため、Phase 27 は、ここで区切り、Phase 28 へ進む(MFA・暗号化は、複数の運営者体制・外部保管を始めるときに、改めて範囲を決める)。

Phase 28 の仕様(`docs/01_phases/phase-28.md`)は、「Core Web Vitals と定期改善。キャッシュ制御、画像・フォント最適化。エラー監視・通知・復旧手順。ブラウザ・自動・アクセシビリティ・性能チェック。PR、自動ビルド、ロールバック」と、高レベルな列挙。Phase 27 と同じ「段階導入」で、複数の PR に分ける。既存の CI(`npm run check`・`npm run audit`)・PR の運用・Cloudflare Pages の自動ビルド(ロールバックは Cloudflare のダッシュボードから)は、すでにある。

## PR1: キャッシュ制御

### 現状の確認(本番の応答ヘッダー)

HTML・CSS・JS・データ・画像のすべてが `Cache-Control: public, max-age=0, must-revalidate`(Cloudflare Pages の既定。ETag で、変わっていなければ 304)。

### 決定

- `public/_headers` を新設し、**画像(`/assets/img/*`・`/favicon.svg`)だけ、1 日(`max-age=86400`)+ `stale-while-revalidate=604800`** で持たせる。
- **JS・CSS・HTML・データ(`/data/*`)・API は、変えない(いつでも再検証)**。理由: ファイル名に版(ハッシュ)がなく、ビルド工程もない(ES Modules を、そのまま配信)ため、長く持たせると、新しい HTML と古い JS の組み合わせ(モジュールの版が混ざる)が起きうる。ファイル名に版を付ける(ビルド工程を入れる)のは、「フレームワーク・バンドラを使わない」方針を変えるため、この PR ではしない。
- `immutable` は付けない(ゲームの画面など、同じパスの画像を撮り直すことがあるため)。1 日で、古い絵が残る期間を抑える。
- Pages Functions の応答(`/api/*`・`/auth/*`)には、`_headers` は効かない(各 Function が、自分で `Cache-Control` を決める。従来どおり)。

### 影響範囲

- 画像の再読み込み(304 の確認の往復)が減る。表示される内容は、変わらない。画像を差し替えたとき、利用者の端末に古い絵が、最大 1 日(+ 再検証の間の最大 7 日の裏側の更新)残りうる。
- 新しい D1 のマイグレーション・環境変数・プライバシーポリシーの変更は、ない。

### テスト結果

- `tests/cache-headers.test.js`(4 件): `_headers` の形・対象が画像だけであること・期限が 1 日・`immutable` がないこと。
- 実際のヘッダー(Cloudflare Pages が `_headers` を読むこと)は、マージ後に、本番の応答で確認する(`curl -I`)。

### この PR でやらないこと(次の PR 以降で、都度範囲を確認)

- Core Web Vitals の計測・フォントの最適化・エラー監視と通知・復旧手順の文書化・性能チェックの自動化・ロールバック手順の文書化。
