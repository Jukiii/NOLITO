# 0044 Phase 19 PR 3: プロフィール公開範囲の設定・オンラインランキング

日付: 2026-09-24 / 対象: Phase 19 PR 3(0042 の計画のとおり)。PR2 と同じく、「全部おすすめで決めて自立で進めて」という運営者の指示により、実装前の確認を待たず、以下を Claude Code の判断で決定した。

## 背景

0042 で、PR3(オンラインランキング)は、ほかの利用者にも見える、新しい種類の公開のため、プライバシーポリシーの改定が必要としていた。また `docs/decisions/0004-phase-03-roles-records.md`(#12)は、「端末内の記録は改ざんできる。端末内ランキングは自分用のため許容。オンラインランキング(P19)では、サーバー側で検証する」と、この Phase で果たすべき約束を、あらかじめ決めていた。

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 参加は任意(既定は不参加) | `users.ranking_opt_in`(既定 0)。アカウントのページの「オンラインランキング」から、チェックボックスで切り替える。不参加に切り替えると、公開されていた記録(下記)も、すぐに消す | 「プロフィール公開範囲の設定」という仕様どおり。既定を不参加にするのは、このサイトの一貫した方針(音・アクセス解析・ゲームのアカウント同期も、既定はオフ/不参加) |
| 2 | 送る内容(データ最小化) | 役職・難易度ごとにクリアしたときの、ニックネーム・称号・スコア・職種(乗り物)だけ。**1プレイごとの詳細な記録(打鍵ごとの集計など)は送らない**(PR2 の game_progress と同じ考え方) | 公開する情報を、ランキングの表示に要る最小限にする |
| 3 | データの形 | 新しいテーブル `ranking_entries`。**1 利用者 × 役職 × 難易度で 1 行**(職種をまたいだ自己ベスト。成績ページの「ハイスコア」= Phase 18 PR4 と、同じ考え方)。役職ごとの記録を何件も並べる、端末内ランキング(Phase 3)とは違う形にした | 「参加した利用者どうしの、上位 N 件」を、SQL の `ORDER BY score DESC LIMIT 10` で、そのまま出せる形にする。1 人が何度もクリアして、上位を何枠も占める、ということが起きない |
| 4 | 送るタイミング | 参加している間、**役職・難易度ごとに、自己ベストを上回ってクリアしたときだけ**、自動で送る(端末内ランキングの記録と同時)。押すボタンはない | 「参加する/しない」の切り替えが、同意の区切り(PR2 のアップロード/ダウンロードのボタンとは、性質が違う操作のため)。自己ベストのときだけ送るのは、無意味な通信を減らすため |
| 5 | **サーバー側の検証(0004 の約束)** | 送られてきたスコアが、その役職で理論上ありうる最大値(目標語数・最大距離・正確率100%・**あり得ないほど速い打鍵**(15打鍵/秒。人が持続して出せる速さより、十分に大きい値)から計算)を超えていたら、断る(`functions/_lib/ranking-limits.js`)。**スコアの式(`score.js` の `SCORE_RULES`)は、公開のものをそのまま使い、重複させない**。役職の構造(目標語数・最大距離・倍率)だけ、小さく複製し、実際の `roles.json` と値がそろっているかを、テストで検査する | 改ざんされたスコアが、オンラインランキングに載ることを防ぐ。1プレイごとの詳細な記録を送らない設計(#2)なので、打鍵ごとの再現・完全な検証はできない。「あり得ない値を、上限で弾く」という、実現できる範囲の検証にした |
| 6 | 閲覧は、ログイン不要 | `GET /api/games/escape-boss/ranking` は、**だれでも見られる**(ログインしていない訪問者も含む)。IP ごとにレート制限する | 「ランキングを見る」ことは、参加者の情報を公開する側の同意(#1)の範囲内。見る側に、アカウントを求める理由がない |
| 7 | 個人を特定する情報は含めない | 応答に、メールアドレス・アカウントの ID を含めない(ニックネーム・称号・スコア・職種・日時だけ)。テストで検査している | 既存の方針(監査ログ・問い合わせなどと同じ) |
| 8 | 画面 | ダッシュボード(`/games/escape-boss/`)に、「オンラインランキング」の節(役職・難易度の選択・上位10件の表。端末内の「ランキング」の節とは別)。アカウントのページへのリンクを添える。アカウントのページに、参加のチェックボックス | 端末内ランキングと、見た目(表)は共通の CSS を使うが、データも選択の状態も別にする(参加していない人にも、常に表示するため) |
| 9 | プライバシーポリシー | **版を 4 に上げる**(6-2-2 を新設)。「参加すると、ログインしていない人を含む、だれでも見られる」ことを、明記する。`analyticsConfig.policyVersion` も 4 にし、既存の同意を無効にする | 「ほかの利用者にも見える」公開は、PR2(アカウントに保存するだけ)より重い性質の変更なので、独立して版を上げた |
| 10 | 監査ログ | 参加の切り替え(`ranking-opt-in-change`)は残す。記録の送信(クリアのたび、自動)は、**残さない**(PR2 の `game-sync-save` と違い、頻繁に呼ばれる、ふつうのプレイ行為のため) | 監査ログを、セキュリティ・プライバシー上、意味のある操作だけに保つ |
| 11 | アカウント削除・不参加 | どちらでも、`ranking_entries` の行を消す(`deleteUser`・`setRankingOptIn`)。D1 は外部キーの `ON DELETE CASCADE` を自動実行しないため、明示的に消す(PR2 と同じ注意) | 公開をやめたら、公開されていた記録も、すぐに消えること |

## 招待制のままでよいか

0042 の想定どおり、**招待制のまま実装した**。アカウントを持つ人(=招待された人)だけが「参加」できる。**閲覧**は、招待の有無に関係なく、だれでもできる(#6)。

## 未確認・既知事項

- 本番の D1 への `migrations/0005_ranking.sql` の適用は、このブランチのマージ後に、運営者の認証情報を使って実施する(0003・0004 と同じ手順)
- スコアの上限(`MAX_CPS = 15`)は、保守的に大きく取った値。将来、スコアの式(`score.js`)を変えたときは、`functions/_lib/ranking-limits.js` と `tests/ranking-limits.test.js` を、あわせて見直すこと
- オンラインランキングの参加者が少ない間は、表がほとんど空になる(「まだ、参加している人がいません」)。これは、既定不参加・任意参加という設計の、意図した結果
- 職種別・役職別の BGM や、称号の見た目の演出強化など、Phase 19 の範囲外の改善は、別Phaseで検討する
