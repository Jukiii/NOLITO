# 0015 Phase 10 PR 1: DB のバックアップの決定事項

日付: 2026-09-20 / 対象: Phase 10「GitHub＋DB定期バックアップ」。Phase 10 は 3 つの PR(バックアップ → 更新履歴 → 問い合わせ)に分ける。この PR は、その1つ目。

## 背景

本番の D1 には、利用者のメールアドレス・ライセンスなど、個人情報が入っている(Phase 9)。コード・記事・商品のデータは GitHub にあるが、**DB は GitHub に置けない**(リポジトリが公開で、バックアップに個人情報が入るため)。

## スコープ

- **含める**: 手元で実行する書き出しスクリプト、書き出したファイルの復元確認、Time Travel と書き出しからの復元の手順書、バックアップに入らないものの一覧
- **含めない**: 自動化(GitHub Actions・Cloudflare の定期実行)、バックアップの暗号化、R2 などへの保管、リモートへの自動復元

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 守り方 | 3 層: GitHub(コード・記事・データ)/ **D1 Time Travel**(自動・無料・直近 7 日。有料プランは 30 日)/ **手元の書き出し**(月に 1 回)。([D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)) | 直近の事故は Time Travel で、DB ごとの喪失・7 日より前は書き出しで戻せる |
| 2 | 自動化しない | GitHub Actions での定期書き出しは、しない | **公開のリポジトリに、本番の DB を読める秘密のトークン**を置くことになる。書き出しの置き場所(GitHub の成果物は、公開のリポジトリでは、誰でも取得できると考える)も、非公開にできない。リスクが、得られる便利さに見合わない |
| 3 | 書き出し | `npm run backup:d1`(`scripts/backup-d1.mjs`)。`wrangler d1 export nolito --remote` を呼ぶ。保存先の既定は、ホームフォルダの `nolito-backups/`。ファイル名は `nolito-d1-<UTC の時刻>.sql` | `wrangler` は、すでに devDependency。SQL ファイルは、どの SQLite・D1 にも読み込める |
| 4 | 保存先はリポジトリの外だけ | リポジトリの中を指定すると、**断る**(パスの区切りで判定。`NOLITO-backups` のような、接頭辞が同じだけの別の場所は、外)。念のため `.gitignore` にも `nolito-d1-*.sql`・`backups/` | 個人情報のコミット事故を、二重に防ぐ |
| 5 | 本物の ID を、コミットしない | `wrangler.toml` の ID は、ダミーのまま(0013 の 17)。本物の Database ID は、環境変数 `NOLITO_D1_DATABASE_ID` か `--id` で渡し、**一時的な設定ファイルを作って** `wrangler --config` に渡す(終わったら削除)。ダミーの ID は、断る | ID は秘密ではないが、リポジトリに入れない方針(本番の設定は、ダッシュボードで管理する) |
| 6 | 書き出したあとの確認 | ファイルを、**メモリ上の SQLite(`node:sqlite`)に、1 つの取引として読み込み**、テーブルごとの件数・整合性(`integrity_check`・`foreign_key_check`)・`migrations/` の全テーブルがあることを確かめる。問題があれば、終了コード 1。**表示するのは、テーブル名と件数だけ**(中身は出さない)。`npm run backup:verify -- <ファイル>` で、いつでも確認できる | 「書き出したが、復元できない」を防ぐ。途切れたファイルも見つかる |
| 7 | 復元の手順 | **A. Time Travel**(7 日以内)、**B. 書き出しから、新しい D1 へ**(新しい D1 を作り、読み込み、`DB` のバインディングを向け直して、再デプロイ)。`npm run d1:remote -- ...` で、`wrangler d1` を、同じ仕組み(一時設定)で実行する。`--id` は環境変数より優先(復元先を、本番と取り違えにくくする)。**最初に 1 回、練習用の D1 で、復元の練習をする**ことを、手順書に入れた | 本番で、初めて試すのは、こわい |
| 8 | 頻度と保管 | **月に 1 回**。保管は、**直近 6 か月分**まで(古いものは削除)。パソコンの外にも、1 つ写す | **削除したアカウントの情報が、古いバックアップに残る**ので、保管期間を区切って、最長 6 か月で完全になくなるようにする(プライバシーポリシー v2 に書く。問い合わせの PR) |
| 9 | ファイルの権限 | 書き出したファイルは、自分だけが読める権限にする(`chmod 600`。Windows では効かない) | 最低限の保護 |
| 10 | バックアップに入らないもの | Cloudflare の環境変数(シークレット)・Google の OAuth クライアント・発行したライセンスキーそのもの(DB にはハッシュだけ)。手順書に、控え方を書いた | 復元に必要だが、DB の外にある |

## テスト結果

- `npm run check` 成功。新規 27 件: D1 の ID(形・ダミーの拒否)、`--id`、一時設定(`pages_build_output_dir` を含まない・注入できない)、ファイル名、保存先(リポジトリの内外・接頭辞だけ同じ場所)、`.gitignore`、**本物の wrangler の出力の読み込みと件数**、引用符・日本語・NULL・文中のセミコロン、空・途切れたファイル・テーブルの欠け・外部キー違反の検出、外部キーの検査が最後にまとめて行われること、コマンド(終了コード・中身を表示しないこと・リポジトリの中の保存先を断ること)、スクリプトが外部へ送らないこと
- 手動: 本物の `wrangler d1 export`(ローカルの D1)の出力を見本にして、検査が通ること。wrangler に、一時設定が渡って、認証の段階まで進むこと(偽のトークンで確認。本番には触れていない)。一時ファイルが残らないこと

## 見つけて直した不具合

- 手順書の復元で `--id` を使う書き方をしたが、`d1-remote` が対応していなかった(`--id` に対応。環境変数より優先)
- テストの誤り(実装の不具合ではない): テーブルの欠けを、行の削除だけで作ろうとして、SQL が壊れた

## 未確認・既知事項

- **本番の D1 への書き出し(`--remote`)と、Time Travel の復元は、未確認**(本番の認証情報がないため)。運営者が、手順書の「最初に 1 回」の練習で確かめる
- `wrangler d1 export` は、大きい DB では時間がかかる・制限がありうる(いまは、小さい)。D1 の書き出しの間は、その DB への書き込みが、一時的に止まる場合がある(小さい間は、問題にならない見込み)
- 書き出しは、手動(月に 1 回)。忘れると、7 日より前に戻せない。カレンダーのリマインダーを、運営者に、お願いしている
- 保管期間(6 か月)は、運営者が、手で守る(自動で削除はしない)
- Node.js 22.13 以上が要る(`node:sqlite`)。CI は Node 22 の最新
