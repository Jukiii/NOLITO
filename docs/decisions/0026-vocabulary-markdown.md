# 0026 Phase 14 PR 1: 語録の Markdown 管理元・検証・確認の状況

日付: 2026-09-21 / 対象: Phase 14「語録に日本語・読み・ローマ字・カテゴリ・難易度・苦手判定・関連用語・学習ポイント。基本短文、難語は詳細説明。AI チェック+人間最終確認。Markdown 追加・管理画面・AI 生成に対応」。

Phase 14 は 2 つの PR に分ける。**この PR(1)**: Markdown の管理元・共通の検証・確認の状況・AI チェックの支え。**PR 2**: 難語の詳細説明・学習ポイント・関連用語の、ゲーム画面での表示(データの項目 `detail` の追加)。

## 仕様と、現状の突き合わせ

| 仕様 | 状態 |
| ---- | ---- |
| 語録の項目(日本語・読み・ローマ字・カテゴリ・難易度・苦手判定・関連用語・学習ポイント) | 項目は、すべてある(Phase 2〜)。`learning_points` は全語で空・画面に未表示 → PR 2 |
| 基本短文、難語は詳細説明 | 短文(80 字以内)だけ。詳細説明は、PR 2 |
| **AI チェック + 人間最終確認** | **この PR**。確認の状況を、原稿に持つ。AI に渡す文と機械の確認結果を、コマンドで出す |
| **Markdown 追加** | **この PR**。管理元を Markdown にし、公開の JSON を生成する(0003 で「Phase 14 で導入」としていたもの) |
| 管理画面 | **作らない**(下記)。同じ検証を使える形にする |
| AI 生成 | AI の API との連携は作らない(下記)。AI が書く形式(プロンプト)と、検証・確認の道を整える |

## 運営者が決めたこと(計画への「推奨案で」)

1. **ローマ字**: 原稿では、**省略できる**(省略すると、読みから作る。既存の語は、そのまま)
2. **確認の状況**: **`draft`(公開しない)と `review`(確認の状況)を持つ**。新しい語は、`draft` から始める
3. **詳細説明**: `detail` を新しく足す(PR 2)
4. **管理画面・AI 生成**: **どちらも、この Phase では作らず、同じ検証の道に乗せる準備まで**。管理画面は Phase 26
5. **PR の分け方**: 2 つ

## 計画からの変更(お伝えしたこと)

計画の「Markdown の読み込み」は、「依存なしの小さな処理」を選んでもらいましたが、**記事の原稿を読む `yaml` パッケージが、すでに開発用の依存として入っていました**(新しいパッケージは、要りません)。自分で YAML の読み取りを書くより、実績のあるパッケージを**厳しい設定**で使うほうが安全なので、そうしました(YAML 1.2 の core スキーマ・同じキーの重複はエラー・別名(アンカー)・型の指定(`!!`)・結合(`<<`)は使えない。読み取ったあとの形は、自作の検証が、すべて確かめる)。「新しいパッケージを足さない」「書き方の間違いを、はっきりエラーにする」という選んだ理由は、満たしています。

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 管理元 | `content/vocabulary/<職種ID>.md`(職種ごとに 1 ファイル)。Markdown の中に、` ```yaml ` で囲んだ語録の YAML を、**ちょうど 1 つ**書く(`docs/04_templates/vocabulary-template.md` の形式)。YAML の外の文章は、自由(見出し・作成メモ・AI への指示) | 仕様のテンプレートどおり。差分が読みやすい |
| 2 | 生成 | `npm run build:vocabulary` が、検証して `public/data/vocabulary/<職種ID>.json` を生成(Prettier で整形)。`--check` で最新かを検査。**生成物もコミットする**(記事と同じ。`npm run check` が検査)。`npm run build` に含める | Cloudflare Pages のビルドは使わない |
| 3 | 既存の 180 語 | 現在の JSON から Markdown に移した。**生成した JSON が、現在の JSON と、まったく同じ**(ゲームへの影響は、なし。テストで検査) | 既存の記録・復習リストが、壊れない |
| 4 | 検証(`vocab-validate.mjs`。DOM・ファイルに触れない) | 必須の項目・未知の項目・型・長さ・`id` の形と重複(職種をまたぐ)・日本語の重複(職種をまたぐ)・読み(ひらがなと長音だけ・入力できる)・**ローマ字が最後まで入力できる(余分な文字が続かない)・先頭が画面に表示する書き方**・難易度 1〜5・役職の実在・説明が「。」で終わる 80 字以内の 1 行・関連用語が同じ職種の、ほかの語(**公開する語は、下書きを指せない**)・学習ポイント(5 個まで各 60 字)・**制御文字・見えない文字**(向きを変える文字・幅のない文字など)。問題は、すべて集めて返す。エラーは、ビルドを失敗させる | 手で書いても、AI が書いても、同じ検証を通す。管理画面(Phase 26)も、同じものを使える |
| 5 | ローマ字の省略 | 省略すると、読みから作る(標準の表記 + 違うときだけ訓令式の表記)。書くときは、先頭が標準の表記 | AI が書くローマ字の誤りを、防ぐ |
| 6 | 確認の状況 | 原稿だけの項目: **`draft: true`(下書き。公開の JSON に入れない)**、**`review: pending / confirmed`**(人間の確認の状況。既定 `pending`)、**`note`**(確認してほしい点。200 字まで)。既存の 180 語は `review: pending` のまま公開を続ける。**運営者が「OK」と言った語だけを、`confirmed` にする**。確認メモ(旧 `docs/vocabulary-review-notes.json`・35 件)は、`note` に移した | 下書きを公開しない。確認の進み具合を、記録する |
| 7 | 確認シート | 原稿から生成(下書き・確認の状況・確認メモを含む)。列「確認」(下書き・未確認・確認済み)と、「人間の確認: 確認済み n 語 / 未確認 n 語」を追加 | 運営者が、確認の進みを見られる |
| 8 | AI チェックの支え | `npm run vocab:check`: 検証の結果・確認の状況・下書きの一覧・確認メモ・警告。`-- --for-ai`: AI に渡す文(`docs/06_ai/content-check-prompt.md` + 機械の確認結果 + 下書きの語の YAML)を出す(`--all` で、未確認の語も)。**AI の結果は、最終判断にしない** | 有料の AI に依存しない(人間の確認が基本)。AI の API とは、連携しない |
| 9 | 文書 | `vocabulary-template.md`(形式・項目の表・足す流れ)・`vocabulary-validation.md`(機械・AI・人間の分担)・`vocabulary-generation-prompt.md`(**`romaji` は書かない・`draft: true` と `review: pending` を付ける・不明点は `note`**)・`content-check-prompt.md`・`dev-setup.md`・`data-model.md`・`CLAUDE.md`。テンプレートの YAML の見本が、検証を通ることを、テストで検査 | 文書と実装を、そろえる |
| 10 | 管理画面 | **作らない**。管理者アカウント・権限管理は Phase 26。この PR は、その入口になる検証の共通化までを行う | 仕様の順序 |
| 11 | 影響 | **ゲーム・記録・バランス・スコアは、変わらない**。公開の語録の内容は、同じ | |
