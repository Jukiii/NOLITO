# 0010 Phase 8 ツールの基盤(保存方式・料金の表示・共通の保存の部品)の決定事項

日付: 2026-09-20 / 対象Phase: 8

## 仕様

`docs/01_phases/phase-08.md`: 無料利用を基本に将来有料機能。ツールごとに保存方式を選択。個人向けから将来チーム対応。

## スコープ

含めるもの: プロダクトの `storage`(保存方式)・`plan`(無料の範囲と将来の有料機能の予定)のデータと検証・表示、`/tools/`(一覧)、ツール共通の保存の部品(`tools/store.js`)、「個人→チーム」に備えた保存先の分け方(ワークスペース)。

含めないもの(該当Phase・別途): **ツール本体**(何を作るかは未定。Issue #15)、有料機能の実際の制御(課金・ライセンス・アカウント。P9・P29)、アカウントへの保存(`account`。P9・P19)、チームの画面・権限・共有(P26 の権限管理が前提)、ナビ「ツール」の有効化(最初のツールを公開するとき)、ゲームの `storage.js` の置き換え(P19)、`/downloads/`(仕様に文面なし)。

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | ツール本体 | 作らない。基盤(データ・表示・保存の部品)だけ | 仕様にツールの中身の指定がない。何を作るかは商品の企画で、運営者が決める。Phase 7 のソフトと同じ進め方 |
| 2 | 保存方式(`storage`) | `none`(保存しない)・`browser`(この端末のブラウザ)・`file`(ファイルの書き出し・読み込み)から、重複なしで1つ以上。`none` は単独。`account` は P9・P19 で加える | 仕様に選択肢の列挙がないため、私が定義した。詳細ページの「データの保存」の節に、方式ごとの説明を出す。カードには「保存」の行 |
| 3 | 料金(`plan`) | `null`(節を出さない)か `{ free, paid }`。無料の範囲(`free`)は1件以上で、必ず示す(無料利用が基本)。将来の有料機能(`paid`)は0件以上で、出すときは「まだ提供していません。内容や時期は、変わることがあります」を添える。各100字まで・10件まで | 仕様「無料利用を基本に将来有料機能」。有料機能は「予定」で、約束にならない表現にする。使えるかどうかの制御は、ライセンスのある P9 以降 |
| 4 | チーム対応 | 保存先を、ツールIDとワークスペースで分ける(キー `nolito:tool:<ツールID>:<ワークスペース>:v1`、既定は `personal`)。チームの画面・権限は作らない。「チーム対応予定」の文言は、公開の文面に載せない | 個人向けの保存が、将来チーム用のワークスペースと混ざらないようにする設計上の備え。公開の文面に書くと約束になる |
| 5 | データの版 | `products.json` は version 4(`storage`・`plan` が加わった。どちらも必須)。ゲームは `storage: ["browser"]`・`plan: null`。ゲームの動作環境の「保存」の行は、「データの保存」の節と重複するので削除した | 版が上がるたびに、旧形式は検証で落ちる |
| 6 | 保存の部品 | `public/assets/js/tools/store.js`(DOM 非依存)。`createToolStore({ toolId, workspace, version, initial, migrations, normalize })` が、`load` / `save` / `update` / `clear` / `exportJson` / `parseImport` / `importJson` を返す。保存の形は `{ version, savedAt, data }` | 「保存方式の選択」に、選べる実体が必要。ツールが増えても、同じ安全な保存にする |
| 7 | 保存の安全性 | ①壊れたデータは上書きせず `:corrupt` に退避(最初の1つを残す)。②このコードより新しい版のデータは、読み込まず、保存・取り込みも拒否する(保存の直前に、毎回、保存されている版を確認する。`load` を呼ばずに `save` しても上書きしない)。③保存できない環境(アクセス拒否・容量超過)では、メモリに残して落ちない(書けたらメモリを捨てる)。④版の移行は、順に適用し、元のデータを `:backup-v<版>` に一度だけ退避。移行がなければ壊れたものとして退避。⑤`normalize` を読み込み・保存・取り込みのたびに通す | 利用者のデータを、勝手に消さない・壊さない。ゲームの `storage.js`(P3・P4)で確立した方針を踏襲 |
| 8 | JSON の書き出し・読み込み | 書き出しは `{ format, toolId, workspace, version, exportedAt, data }`。取り込みは、サイズ(1MB。バイト数で数える)・JSON・形式・ツールID・版・中身(`normalize`)を順に検査し、理由つきで拒否する。取り込むと、置き換える前のデータを `:before-import` に退避する。ワークスペースは、書き出した先と違ってもよい。壊れた・新しい版のデータは、書き出さない(null) | 利用者が書き換えられる入力なので、安全側に倒す。`__proto__` を含むデータで、`Object.prototype` が汚れないことを確認済み |
| 9 | ゲームの保存 | 変更しない | ゲームには、独自の移行・集計がある。統合は、アカウントへの移行(P19)で検討 |
| 10 | `/tools/` とナビ | 一覧ページを作る(いまは0件)。ナビの「ツール」は「準備中」のまま | 空のページへ誘導しない。切り替えは `nav.js` の1行 |

## 確認中に見つけたこと

- レビューで、保存の部品の穴を2つ塞いだ(いずれも、修正後のテストで確認済み): ①「新しい版のデータを守る」状態を、`load` を呼んだ後だけ持っていたため、`load` を呼ばずに `save`・取り込みをすると上書きできた → 保存の直前に、毎回、保存されている版を確認する形に変更。②保存できたあとも、古いメモリのデータを持ち続けていた(他のタブがデータを消したあとに、古いデータを返す) → 書けなかったときだけ、メモリを持つ形に変更
- テストの誤りが3件(実装の不具合ではない): ワークスペースの省略(既定値)を不正な値と取り違えた、ヘッダーの注意書きの確認が料金の節の注意書きに当たった、見本のテスト用ページに favicon がなく 404 になった

## 未確認・既知事項

- ツールが実際にない(Issue #15)。保存の部品は、テスト用のメモのページ(一時コピー。リポジトリには入れない)でだけ確認した。最初のツールを作るときに、必要な API の過不足が見つかる可能性がある
- 保存の部品の JSON の書き出し(ファイルのダウンロード)・読み込み(ファイルの選択)の画面は、ツールごとに作る(部品は文字列だけを扱う)
- 複数のタブが同時に保存したときの衝突の解決(後勝ち)は、`update` が毎回読み直す範囲まで。厳密な排他制御はしていない
- 将来の有料機能の文言は、ツールごとに運営者が決める。有料機能の提供を始めるときは、Issue #12(販売・特定商取引法・規約)も決める
- アカウントへの保存・チームでの共有は、未対応(P9・P19・P26)
