# 0049 Phase 24 の計画(語録の拡張ファイル・役職/難易度専用語)

日付: 2026-09-26 / 対象: Phase 24「基本語録＋難易度・役職拡張ファイル」

Phase 24 の仕様書(`docs/01_phases/phase-24.md`)は一行の要約のみで、実装方針の解釈が複数成り立ったため、着手前に Issue #85 を作成し、運営者に確認した。運営者は、チャット上で **候補B(役職・難易度ごとの専用語)** を選択した。この決定は、既存の決定ログ 0021(「役職ごとの語の出し分けはしない」)・Phase 17 PR1(「語は削らない: 180 語すべてが、どの役職でも出うる」)を、**専用語という新しい仕組みで上書きする**運営者の承認済みの判断である。

## 現状の確認(着手前の点検)

- **役職による出し分けの土台は、すでにある**。原稿の各語は、もともと `roles`(出題する役職の id の一覧)を **必須**で持っており、いまの 180 語は、すべて `roles: [senpai, kakaricho, buchou, shachou, kaicho]`(5 役職すべて)。ゲーム側も、`vocabulary.js` の `pickWords` が `items.filter((item) => item.roles.includes(roleId))` で、**すでに役職ごとにフィルタしている**(0021 の「出し分けない」は、単に「全語に全役職を書く」ことで実現されていた)。つまり、**役職専用語は、スキーマ変更なしで、`roles` に一部の役職だけを書けば、そのまま動く**。
- **難易度(むずかしい 等)による出し分けは、土台がない**。語の `difficulty`(1〜5の整数。読みの長さの決め)は、役職の中の「出やすさの重み」(`roles.json` の `stage.word_weights`)にしか使われておらず、**選択された難易度(やさしい/ふつう/むずかしい。`difficulties.json`)による出題対象の絞り込みは、いまは存在しない**(`main.js` の `beginGame` は `difficultyId` を持っているが、`pickWords` には渡していない)。ここが、この Phase で追加する、唯一の新しいスキーマ。
- 「拡張ファイル」は、**追加する語を、既存の職種ごとの原稿ファイル(30語・安定した内容)とは別のファイルに書けるようにする、原稿の運用上のしくみ**と決めた(候補A由来)。候補Bの専用語を、これで届ける。

## 決定

| # | 項目 | 決定 | 理由 |
| - | ---- | ---- | ---- |
| 1 | 役職専用語 | **新しいスキーマ変更は、なし**。`roles` に、対象の役職だけを書く(例 `roles: [kaicho]` で、会長だけに出る)。既存の 180 語(`roles` が 5 役職すべて)は、変更しない | 既存のしくみ(`pickWords` のフィルタ)が、そのまま使える。0021 の「出し分けない」は、「その語は、いまは全役職で使う」という**個別の語の設定**であって、しくみ自体を禁止していたわけではないと解釈した |
| 2 | 難易度専用語 | 語に、新しい任意項目 **`difficulties`**(`difficulties.json` の id の一覧。省略すると、すべての難易度で出る)を追加する。`pickWords` に `difficultyId` を渡せるようにし、`items.filter(item => item.roles.includes(roleId) && (!item.difficulties || item.difficulties.includes(difficultyId)))` で絞り込む | 役職(`roles`)と対になる、もう一つの出し分け軸。省略時は「すべて」なので、既存の 180 語は影響を受けない(後方互換) |
| 3 | 拡張ファイルの形式 | 職種ごとの**ベースの原稿**(`content/vocabulary/<職種ID>.md`。既存のまま、`job_id`・`job_name`・`version`・`updated_at`・`items` を持つ)に加えて、**拡張ファイル**(`content/vocabulary/<職種ID>.ext-<任意の名前>.md`。**`job_id` と `items` だけ**を持つ、軽い形)を、同じ職種に何個でも足せるようにする。`npm run build:vocabulary` が、ベース + すべての拡張ファイルの `items` を**マージしてから検証**し、1 つの `public/data/vocabulary/<職種ID>.json` にする | 既存の 30 語のファイルを直接編集せず、追加分だけを別ファイルに書ける(差分が小さく、レビューしやすい)。`job_name`・`version`・`updated_at` は、ベースの原稿だけが持つ(拡張ファイルごとにバージョンがバラつかない) |
| 4 | 検証 | マージした語の一覧を、**既存の `validateVocabulary` にそのまま通す**(項目の形式・id/日本語/読みの重複・関連用語の参照は、ベース+拡張をまたいで検査される。新しい検証ロジックの追加は最小限)。拡張ファイル自身は、`job_id` の一致・`items` 以外の項目がないこと・対応するベースの原稿があることだけ、別途チェックする | 検証の二重実装を避ける(`vocab-validate.mjs` の変更を、`difficulties` 項目の追加だけに絞る) |
| 5 | id・バランス | **語の id は、消さない・つけ替えない**という既存ルールは、専用語にもそのまま適用する(`<職種ID>-031` から連番で続ける)。**役職・難易度で語を絞ると、対象の役職・難易度だけ、語の候補数が増減する**。実際に専用語を追加(下書きの確認を経て公開)するときは、その役職・難易度の組み合わせについてだけ、`tests/balance.test.js` のシミュレーションで、クリア率の階段(0006・0017)への影響を確認する(このPRでは、まだ公開する専用語を追加しないため、対象なし) |
| 6 | このPRのスコープ | **しくみ(スキーマ・ビルド・検証・出題ロジック)だけを実装し、実際の専用語(下書き含む)は、まだ追加しない**。合成した原稿(テスト用のダミーデータ)だけで、しくみを検証する。実在の `content/vocabulary/*.md`・`public/data/vocabulary/*.json` は、この PR では変更しない | 実際の語の追加は、AI下書き→人間の確認(0026の方針)を経る、別の作業。しくみと内容を分けることで、この PR のレビュー範囲を、安全な基盤部分だけに絞れる |

### 除外(この PR ではやらないこと)

- 実際の役職・難易度専用語の追加(下書きも含め、次の PR 以降)
- `docs/vocabulary-review.md`(確認シート)・`npm run vocab:stats` の、専用語向けの表示変更(専用語が実在するようになってから、必要に応じて対応する)
- 候補C(難易度・役職そのものを増やせるようにする)・候補D(AI/管理画面向けの差分ファイル)は、今回のスコープ外(運営者は候補Bのみを選択)

### テスト結果

- `npm run check`(lint・Prettier・単体テスト): **全 1982 件、成功**。実在の `content/vocabulary/*.md`・`public/data/vocabulary/*.json` は、この PR では変更していない(公開している 180 語・6 職種は、そのまま)
- **スキーマ**: `vocab-validate.mjs` に、任意項目 `difficulties`(難易度 id の一覧。実在チェック・重複チェックつき。`detail` と同じ「あるときだけ、公開の JSON に入る」扱い)を追加。`vocab-md.mjs` の YAML 書き出しも対応
- **拡張ファイルの仕組み**(`vocab-build.mjs`): `loadSources` が、`<職種ID>.ext-<名前>.md` を拡張ファイル(`kind: "ext"`)として認識。`readSources` が、ベース + すべての拡張ファイルの `items` をマージしてから、既存の `validateVocabulary` に 1 回だけ通す(id・日本語・読みの重複、関連用語の参照は、ベース・拡張ファイルをまたいで検査される)。拡張ファイル自身の構造(`job_id`・`items` だけ、対応するベースがあること)も検査する。新規テスト、合成した原稿で 8 件・`loadSources` の分類で 1 件
- **出題ロジック**(`vocabulary.js`): `pickWords` に `difficultyId` を追加。`roles`(既存)と `difficulties`(新規)の、両方を満たす語だけを候補にする(省略した語は、これまでどおり、すべての役職・難易度が対象)。`main.js` の `beginGame` から、解決済みの `difficulty.id` を渡す。新規テスト 2 件(単体)・既存の静的配線テスト(`game-page.test.js`)を更新
- **用語確認(check モード)は、意図して対象外**: `check.js` の `pickCheckWords` は、そもそも役職・難易度の選択がないモードなので、専用語も含めて、すべての語を対象のままにした(仕様変更ではなく、既存の設計の帰結)
- **バランスへの影響は、なし**(このPRでは、実際の専用語を追加していないため。追加時は、対象の役職・難易度の組み合わせについてだけ、シミュレーションで確認する)
