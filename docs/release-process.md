# リリースの進め方(小機能単位のテスト公開)

Phase 10 の方針「小機能単位でテスト公開」を、実際の手順にしたものです。これまでの進め方(Phase 8 の「キーみち」を、2つの PR に分けて公開した、など)を、そのまま書きました。チェックリストは `docs/05_checklists/release-checklist.md`。

## 考え方

- **小さく作って、小さく公開する。** 1つの機能を、1つの PR にする(Phase の中でも、分ける)。大きな変更を、まとめて公開しない。
- **公開したものは「テスト版」と示す。** `products.json` の `status: "beta"`(画面には「テスト版」と出る)。安定してから `released`(公開中)にする。
- **利用者に、変わったことを伝える。** 公開のたびに、更新履歴に書く(下記)。書けば、`/updates/` に、自動で出る。
- **すぐ戻せるようにする。** 1つの PR は、`git revert` か、Cloudflare のロールバックで、戻せる大きさにする。

## 1つの機能を公開する流れ

1. **計画**: 変更するファイル・テスト方法を、先に確認する(`CLAUDE.md` の作業ルール)。仕様にないものは足さない。未確定のことは、Issue にする。
2. **実装**: `phase-NN-<name>` ブランチで作る。ロジックを変えたら、テストも書く。
3. **更新履歴に書く**(プロダクトを変えたとき):
   - `public/data/products.json` の、そのプロダクトの `version` を上げ、`changelog` の**先頭**に、新しい項目(バージョン・日付・変更点)を足す(先頭のバージョンと `version` は、同じにする。検査される)。
   - `npm run build` で、詳細ページを作り直す(生成物も、コミットする)。
   - これで、詳細ページの「更新履歴」と、**`/updates/`** に、自動で出る。
   - 記事を公開・更新したときは、記事の `date`・`updated` が、そのまま `/updates/` に出る。
4. **確認**: `npm run check`(lint・整形・テスト)を通す。本物のブラウザで、画面・スマホの幅・キーボード操作を確認する。
5. **PR**: テンプレートに沿って書く(概要・テスト結果・画面確認・セキュリティ確認・未対応事項)。データベースの変更(`migrations/`)があれば、**マージの前に、本番の D1 に、その SQL を実行する**ことを、冒頭に書く(`docs/auth-setup.md`)。
6. **プレビューで確認**: PR ごとに、Cloudflare のプレビュー(URL)ができる。設定のない環境でも壊れないことを、確認する(アカウント・問い合わせなどの機能は、設定がなければ「準備中」になる)。
7. **マージ → 本番の確認**: 主要なページが 200 で、同意の前に Google へ通信しないこと(アクセス解析の性質)を、確認する。ブランチは、削除しない。

## 大きな変更の前(データベース)

- `migrations/` を適用する前・大きなデータの変更の前に、`npm run backup:d1` で、バックアップを取る(`docs/backup.md`)。
- 直近 7 日以内の間違いは、D1 の Time Travel で戻せる。

## 戻し方

| 状況 | 戻し方 |
| ---- | ---- |
| 公開した変更に、不具合があった | 修正の PR を出す(小さく直せる場合)。すぐに戻したいときは、その PR の **Revert** を、新しい PR として出す(`main` に、直接コミットしない) |
| 至急、直前の状態に戻したい | Cloudflare → Pages → **Deployments** → 以前の本番デプロイ → **Rollback**(サイトの状態だけ。データベースは、戻らない) |
| データベースを、間違って変えた | `docs/backup.md`(Time Travel / 書き出しから) |
| アカウント機能に、問題がある | 環境変数 `AUTH_ENABLED` を `false` にして、再デプロイする(緊急停止。`docs/auth-setup.md`) |

## 「テスト公開」で、利用者に約束すること

- **テスト版**の表示を出す。不具合や、仕様の変更がありうることを、詳細ページに書く。
- **記録が消えない**ようにする。保存の形を変えるときは、版を上げて、古いデータを読めるようにする(`CLAUDE.md`)。
- 不具合の報告・要望は、問い合わせ(Phase 10 の PR 3 で作る)と、アクセス解析(同意した人だけ)を、改善の材料にする。
